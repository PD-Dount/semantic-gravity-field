# 算力服务器运行手册（field_sim）

这台机器上跑出来的结论只覆盖 N ≤ 256 的静态/半静态区间。下面这套模拟器是为**跨过 N≈1900 拐点**
准备的，已经做过三件事：向量化（无 Python 逐 token 循环）、设备无关（cpu/cuda/npu）、可分片续跑。

## 0. 先估，再跑

```bash
python -m field_sim.sweep --preset repulsion --out results/phase_rep.jsonl --estimate
```
打印单个 config 的耗时和整盘外推，**永远先跑这一步**。本机（4 核 CPU, N=256, 120 迭代）是 0.17 s/config。

## 1. 三组预设

| preset | 网格 | config 数 | 用途 |
|---|---|---|---|
| `repulsion` | κa∈{0.1,0.3,1,3} × κr∈{0,0.25,0.5,1,2,4} × 3 seeds | 72 | 主相图：有没有 K 簇吸引子 |
| `repulsion_sparse` | 同上 × top-16 截断 × κr∈{0,0.5,1,2} | 48 | 硬稀疏能否替代排斥 |
| `scale` | κr∈{0,0.5,1} × N∈{1024,4096,8192} | 9 | 规模外推（真机才跑得动） |

## 2. 服务器上的标准跑法

```bash
# 单卡：直接跑
python -m field_sim.sweep --preset repulsion --out results/phase_rep.jsonl --device cuda

# 8 卡：一条命令铺满，每卡一个分片，写同一个 jsonl（互相去重、各自追加）
for i in $(seq 0 7); do
  python -m field_sim.sweep --preset repulsion --device cuda:0 \
      --shard $i --shards 8 --out results/phase_rep.jsonl &
done; wait

# 昇腾：装好 torch_npu 后 device=npu 即可，代码里 already 有探针
python -m field_sim.sweep --preset scale --device npu --out results/phase_scale.jsonl
```

断点续跑是内建的：`--out` 指向的 jsonl 里已有的 config 会被跳过，所以中断后重跑同一行命令即可。

## 3. 出图

```bash
python -m field_sim.report        # -> results/phase_repulsion.png
```

## 4. 显存/时间预算（N² 张量的硬约束）

`cluster_labels` 和 logits 各要一个 N×N fp32 张量。**每 N=4096 约 67 MB/张，N=8192 约 268 MB/张**，
一次前向里同时活的 N² 张量约 4–6 个，所以：

| N | 峰值（估） | 单 config（120 迭代） |
|---|---|---|
| 1024 | ~0.3 GB | 秒级 |
| 4096 | ~1.5 GB | 十几秒 |
| 8192 | ~6 GB | 1–2 分钟 |
| 16384 | ~24 GB | 不建议，需要分块 |

N ≥ 8192 时把 `cluster_iters` 从 64 降到 16，或把 `cluster_tau` 调高（图更稀、连通分量收敛更快）。

## 5. 三个不要踩的坑

1. **不要把 dtype 换成 bf16/fp16。** 聚类判据是 `cos > tau` 的硬阈值，半精度下 0.9 附近的取值抖动
   会让簇数在 1 和 N 之间跳，相图直接失效。矩阵乘不是瓶颈，保持 fp32。
2. **`kappa_r=0` 的列一定是"全坍缩"**，那是基线不是结果，出图时保留它做对照。
3. **`final_clusters` 小不代表成功**：强度够大时场会把整个集合吃光，剩 3 个单元时 NMI 恒为 1.0。
   判据必须同时看 `final_units`（本机实测：存活 ≥32 的配置里 K-state 只占 0–14%）。

## 6. N≥1900 之后稀疏能不能兑现成端到端收益 —— 已验证：不能

> 本节原为"待验证"，2026-11-07 已在两台真机上跑完，结论写定。下次改动本节需要新的实测数据。

### 6.1 验证范围（两次真机，代码 zero-change）

| 侧 | 机器 | 软件栈 | 覆盖内容 |
|---|---|---|---|
| CPU | 华东一区昆山，X86 7185 32C，16 进程 | Python 3.8.10 / torch 2.4.1+cpu / fp32 | 12 项契约、N=256 相图复现、N=8192 规模外推、长序列成本 |
| 加速器 | 华中一区 A 区，异构加速卡 BW（68.7 GB） | Python 3.11.9 / torch 2.9.0+HIP 6.3 / fp32 | 12 项契约、长序列成本、显存峰值 |

**契约两侧都是 12/12 PASS**，且 `A0 == 原生 softmax` 的 `maxerr = 0.00e+00`（CPU 与 DCU 均为 0）。
fp32 判据未被破坏，下面所有比值可比。

同时复现了本机结论：N=1024/4096/8192 × κr∈{0,0.5,1} 共 9 个配置**全部 `clusters=1`、`NMI=0.00`**；
N=256 相图上 dense 的 κr=0 列 12/12 全坍缩、κr>0 的 K-state 0/60（0%）。
**"能不能长出层级"这个问题已经有答案，是负的。**

### 6.2 长序列单步成本（batch 4，fp32，3 次中位数）

| seq | arm | 加速器 ms | 加速器 vs A0 | CPU ms | CPU vs A0 |
|---|---|---|---|---|---|
| 512 | A0 | 11.9 | 1.00× | 175.2 | 1.00× |
| 512 | A2 | 21.1 | 1.77× | 522.1 | 2.98× |
| 512 | A3 | 28.7 | **2.42×** | 550.1 | 3.14× |
| 512 | A4 | 30.6 | **2.58×** | 593.9 | 3.39× |
| 1024 | A0 | 13.4 | 1.00× | 586.4 | 1.00× |
| 1024 | A2 | 45.8 | 3.41× | 1946.8 | 3.32× |
| 1024 | A3 | 53.4 | **3.98×** | 2111.0 | 3.60× |
| 1024 | A4 | 57.4 | **4.28×** | 2474.6 | 4.22× |
| 2048 | A0 | 37.3 | 1.00× | 2178.6 | 1.00× |

两条曲线在 **seq≈1024 交叉**：短序列上加速器还略占便宜（A0 太小、kernel 启动开销占比高），
一旦到 1024 以上，**A0 被融合 SDPA 加速得越多，场项的相对代价就越难看**。

### 6.3 显存：A4 的压缩零收益

| seq=2048 | A0 | A2 | A3 | A4 |
|---|---|---|---|---|
| peak_MB | 3 084 | 12 260 | 12 554 | 12 555 |
| kv_len | 2048 | 2048 | 2049 | **1 442（−30%）** |
| fwd+bwd ms | 37.3 | 155.3 | 180.1 | **195.4（比 A3 慢 8.5%）** |

A4 把 kv_len 压掉 30%，显存与 A3 **完全持平**，延迟反而更差。峰值由稠密的 N² 场/score 张量决定，
不是 KV 缓存——**这条压缩路径在当前实现下只付出开销、不换内存**。

### 6.4 结论（三条）

1. **倍率随 N 单调上升，且在加速器上更差**：A3 2.42→3.98→4.83×，A4 2.58→4.28→5.24×，
   同一 N 下均高于 CPU 侧。demo 里"2.6–3.1×、N 大了会好转"的乐观假设被反向证伪。
2. **原因是结构性的，不是调参能修的**：A0 走融合 SDPA，加速比 14.7→43.8→**58.4×**；
   A3/A4 的场项是 eager 逐元素运算（`cos`、硬阈值、质量再归一），加速比只有 19.2→39.5→50.1× /
   19.4→43.1→47.8×。差出来的那 10 个百分点随 N 放大，比值必然爬升。
3. **"场机制不可训练"是错的，"场机制相对越来越贵"是对的**：seq=2048 的 A4 单步从 CPU 9.35 s
   降到 195 ms（**47.8×**）。绝对墙钟大幅改善，但**等墙钟口径下 A3/A4 追不平 A0**。

因此原始判据——"A3 在等墙钟口径下追平 A0 才算具备工程意义"——**未通过**。

### 6.5 给研发的架构调整建议（按性价比排序）

1. **停止在 A3/A4 上做等墙钟调参**。倍率随 N 单调升是结构性的，再多调一次超参不会翻转结论；
   L20 上的数值重测只用于"记录最终数字"，不用于"看还有没有机会"。
2. **把项目叙事从"用场换稀疏/换算力"改成"用场换可解释性/鲁棒性"**，并在任何宣传材料里
   按 **5× 成本**标注（N=2048 实测 5.24×）。继续用"省算力"讲故事会在客户侧翻车。
3. **唯一有技术含量的降本方向是融合 kernel**：把 `cos + 硬阈值 + 质量归一` 写成一个融合算子
   （Triton / TileLang），让场项与 SDPA 并排吃满带宽。当前 eager 是主要浪费来源，这是能把 4.8× 往下压的
   唯一杠杆。
4. **第二杠杆是分块（chunked / flash 式）场计算**，直接消除 N² 稠密张量。这是唯一能**同时**降显存
   和延迟的方向；A4 的 KV 压缩已被证明无效，不要再在这条路上投人力。
5. **设收口线**：融合 kernel 实现后，若 N=2048 上 A3 仍 >2× A0，则正式收口该分支，A0 作为唯一可交付基线。

### 6.6 这组数据的边界（引用时必须带上）

- **L20 侧未测**：昆山 L20/4090 资源组持续 `0/8`、`0/4` 空闲，未抢到卡；上述加速器数据来自 DCU BW。
  "倍率在加速器上更高"是跨架构的强趋势（融合算子 vs eager 的结构性差异），但 L20 精确数值待补。
- 只测单步 fwd+bwd，**未跑完整训练的墙钟与收敛曲线**；batch=4、单 seed、单卡。
- DTK 的 fp32 与 CUDA 不保证逐位一致，故加速器侧数据标注为"DCU 侧定论"，不与 L20 混用。

三条硬约束不变：fp32、κr=0 列保留做对照、判据必须同时看存活单元数。
